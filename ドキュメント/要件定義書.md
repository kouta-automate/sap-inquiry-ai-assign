## 問い合わせ受付・AI仮アサインシステム（ハッカソン・ローカルデモ版）

| 項目 | 内容 |
|------|------|
| プロジェクト名 | 問い合わせ受付・AI仮アサインシステム |
| 作成日 | 2026-06-05 |
| バージョン | ローカルデモ版（パターンB：AIモック構成） |
| 目的 | SAP運用保守における問い合わせ対応のアサイン業務をAIで自動化する。本バージョンはハッカソンでのデモンストレーションを目的とする |

---

## 0. 本バージョンの方針（重要）

> **このバージョンの最優先事項は「ハッカソンでローカル動作のデモンストレーションができること」である。**
>
> - **デプロイは行わない。** SAP BTP（Cloud Foundry / Kyma）へのデプロイ作業は本スコープに含めない。`cds watch` によるローカル実行のみで完結させる。
> - **デモに必要な範囲を超えた作業は行わない。** 認証、通知、CI/CD、本番DB（HANA Cloud）接続、監視などは実施しない。
> - **AIはモック実装（パターンB）とする。** 実際のLLM（Generative AI Hub）には接続せず、固定の分析結果・候補を返すダミー関数で代替する。これによりBTPアカウントやAI Core契約がなくても全フローを動作させられる。
> - **ただし、後からパターンA（実AI接続）へ切り替えられる構造にしておく。** AI呼び出しは関数として分離し、環境変数のフラグ1つでモック／実接続を切り替えられるようにする。切り替え時にアプリ本体（画面・API・DB処理）の修正は発生しない。

---

## 1. システム概要

SAP運用保守会社において、顧客からの問い合わせを受け付け、AIが内容を分析・分類し、メンバーのアサイン状況を考慮した上で担当者を仮アサインするシステム。仮アサイン結果は上長が承認することで確定する。

本バージョンはSAP CAP（Cloud Application Programming Model）でローカル実行し、AI処理はモックで代替する。

### フロー概要

```
顧客 → 問い合わせ入力 → ローカルDB(SQLite)保存 → AI①（内容分析・分類：モック）
     → AI②（担当候補選定：モック）→ 上長承認 → アサイン確定 → Slack通知
```

## 4. 画面詳細

### 4-1. 問い合わせ入力画面

#### 概要
顧客が問い合わせを起票する画面。認証は不要。

#### 入力項目

| フィールド名 | 種別 | 必須 | 備考 |
|------------|------|------|------|
| 会社名 | 入力フィールド | ○ | 顧客の会社名 |
| 担当者名 | 入力フィールド | ○ | 問い合わせ担当者の氏名 |
| 問い合わせ種別 | ドロップダウン | ○ | 障害 / 質問 / 要望 / 権限申請 / その他 |
| 優先度 | ラジオボタン | ○ | 高 / 中 / 低 |
| 対応希望日 | DatePicker | - | 対応を希望する期限日（任意） |
| 件名 | 入力フィールド | ○ | 問い合わせのタイトル |
| 問い合わせ内容 | TextArea | ○ | 詳細な問い合わせ内容 |

#### 自動生成項目（画面には非表示）

| フィールド名 | 内容 |
|------------|------|
| 問い合わせID | システムが自動採番（例：INQ-20260605-001） |
| 起票日時 | 送信時のシステム日時を自動設定 |
| ステータス | 初期値：「AI分析中」 |

#### 動作
1. 顧客が各項目を入力し「送信」ボタンを押す
2. CAPサービス経由でローカルDB（SQLite）に保存される
3. 送信完了メッセージを表示する
4. 非同期でAI①（モック）が実行される

### 4-2. 上長承認画面

#### 概要
AI仮アサイン結果の一覧と詳細を確認し、承認操作を行う画面。Fiori Elements の List Report / Object Page で実装する。

#### 一覧表示項目

| フィールド名 | 備考 |
|------------|------|
| 問い合わせID | |
| 件名 | |
| 問い合わせ種別 | |
| 優先度 | |
| 起票日時 | |
| ステータス | AI分析中 / 承認待ち / 承認済み |

#### 詳細表示・承認操作

**問い合わせ情報**
- 会社名、担当者名、種別、優先度、件名、内容

**AI①分析結果（モックが返す固定値）**
- 問い合わせ要約
- 簡易回答
- 必要スキル
- 不足情報

**AI②仮アサイン候補（モックが返す候補3名）**

| 順位 | 担当者名 | スキル | 担当領域 | 現在対応件数 | アサイン理由 |
|------|--------|--------|---------|------------|------------|
| 1位 | ○○ | ... | ... | N件 | ... |
| 2位 | ○○ | ... | ... | N件 | ... |
| 3位 | ○○ | ... | ... | N件 | ... |

**承認ボタン**
- 「承認する」ボタンを押すと1位候補がアサイン確定
- ステータスが「承認済み」に更新される
- 承認完了と同時にSlack通知が送信される（後述 §4-3）

---

### 4-3. Slack通知

#### 概要
承認操作が完了した直後、Slack Incoming Webhookを通じて指定チャンネルへ通知を送信する。通知はアサインされたメンバーが担当内容を即時把握することを目的とする。

#### 通知タイミング
- `approve()` アクション実行後に非同期で送信
- 通知失敗（ネットワーク不通等）があっても承認処理には影響しない（ログのみ出力）

#### 通知内容

| 項目 | 内容 |
|------|------|
| アサイン担当者 | 確定したメンバーの氏名 |
| 問い合わせ番号 | INQ-YYYYMMDD-連番 |
| 件名 | 問い合わせの件名 |
| 会社名・担当者名 | 顧客側の情報 |
| 種別・優先度・対応希望日 | 問い合わせ属性 |
| 問い合わせ内容 | 顧客が入力した本文 |
| AI分析結果① | 要約・必要スキル・簡易回答 |

#### 設定
- `.env` の `SLACK_WEBHOOK_URL` にSlack Incoming Webhook URLを設定
- 未設定の場合は通知をスキップ（コンソールにログ出力）

## 5. AI処理仕様（パターンB：モック）

### 基本方針
AI①・AI②は、実際のLLMを呼ばず、**固定の結果を返すモック関数**で実装する。デモ上は「AIが分析・選定した結果」として表示されるため、見た目・操作感は実AI接続時と同一になる。

### 切替設計
- AI呼び出しは `analyzeInquiry()` / `assignMembers()` という関数に分離する。
- 環境変数 `USE_MOCK_AI`（`true`/`false`）でモックと実接続を切り替える。
- 本バージョンでは `USE_MOCK_AI=true` 固定で運用する。
- 関数の**入力と出力（JSON構造）は実接続時と同一**に保つ。これにより呼び出し側（CAPハンドラ・画面）は切替の影響を受けない。

---

### AI① ：問い合わせ内容分析（モック）

| 項目 | 内容 |
|------|------|
| トリガー | 問い合わせ保存後に非同期実行 |
| 入力 | 問い合わせ種別、件名、問い合わせ内容 |
| 実装 | 固定の分析結果を返す（種別に応じて数パターン用意してもよい） |

**出力項目（実接続時と同一構造）**

| 出力項目 | 内容 |
|---------|------|
| 要約 | 問い合わせ内容の要約（モック固定文） |
| 簡易回答 | 一般的な対処法（モック固定文） |
| 必要スキル | 必要スキルのリスト（モック固定値） |
| 不足情報 | 確認すべき情報（モック固定文） |

---

### AI②：担当者アサイン（モック）

| 項目 | 内容 |
|------|------|
| トリガー | AI①完了後に自動実行 |
| 入力 | AI①の出力（必要スキル）＋メンバーDB |
| 実装 | メンバーDBから固定ロジックまたは固定値で候補3名を返す |

**出力項目（実接続時と同一構造）**
- アサイン候補3名（順位付き）
- 各候補のアサイン理由

> 補足：モックでも、メンバーDBの内容を使って「スキル一致するメンバーを件数順に3名返す」程度の簡易ロジックを入れると、デモの説得力が増す（ただし任意）。

## 6. データベース仕様（ローカル：SQLite）

データはローカルのSQLite（インメモリ）に格納する。エンティティはCAPのCDSで定義する。`[production]`プロファイルでのみHANA Cloudに切り替わる設定とするが、本バージョンでは使用しない。

### エンティティ①：Inquiries（問い合わせ）

| フィールド名 | 型 | 説明 |
|---------|-----|------|
| ID | UUID | 主キー |
| inquiryNo | String(20) | 問い合わせ番号（INQ-YYYYMMDD-連番） |
| createdAt | Timestamp | 起票日時（managed） |
| companyName | String(100) | 会社名 |
| contactName | String(100) | 担当者名 |
| inquiryType | String(20) | 障害/質問/要望/権限申請/その他 |
| priority | String(10) | 高/中/低 |
| desiredResponseDate | Date | 対応希望日（null可） |
| subject | String(200) | 件名 |
| content | LargeString | 問い合わせ内容 |
| status | String(20) | AI分析中/承認待ち/承認済み |
| aiSummary | LargeString | AI①要約 |
| aiAnswer | LargeString | AI①簡易回答 |
| aiRequiredSkills | String(200) | AI①必要スキル（カンマ区切り） |
| aiMissingInfo | LargeString | AI①不足情報 |
| assignedMember | Association → Members | 承認確定後の担当者 |
| assignedAt | Timestamp | 承認日時 |

### 子エンティティ：AssignCandidates（仮アサイン候補）

| フィールド名 | 型 | 説明 |
|---------|-----|------|
| ID | UUID | 主キー |
| inquiry | Association → Inquiries | 親問い合わせ |
| rank | Integer | 順位（1〜3） |
| member | Association → Members | 候補メンバー |
| reason | LargeString | アサイン理由 |

### エンティティ②：Members（メンバー）

| フィールド名 | 型 | 説明 |
|---------|-----|------|
| ID | UUID | 主キー |
| memberNo | String(10) | メンバー番号（M001〜） |
| name | String(100) | 氏名 |
| skills | String(200) | スキル（カンマ区切り） |
| domain | String(100) | 担当領域 |
| currentCases | Integer | 現在の対応件数 |
| status | String(10) | 対応可/対応中/不在 |

> Members はデモ用の初期データ（CSVシード）を db/data/ に用意し、起動時に投入する。

- **SAP BTPへのデプロイ作業全般**（Cloud Foundry / Kyma）

- RAG（Document Grounding）
- Slack以外の通知手段（メール、Teams等）

## 11. 将来のパターンAへの移行に必要な作業（参考）

本バージョンを完成させた後、時間が余った場合にのみ実施する想定。アプリ本体の改修は不要。

1. SAP BTPでSAP AI Core（Extendedプラン）インスタンスを作成
2. サービスキーを取得し、`AICORE_SERVICE_KEY`（.env）に設定、または `cds bind`
3. `ai-handler.js` の実接続側関数（既に枠は用意済み）を有効化
4. 環境変数 `USE_MOCK_AI=false` に変更
5. `cds watch --profile hybrid` で起動

> デプロイは移行後も不要。「ローカル実行＋AI呼び出しのみクラウド」で動作する。
